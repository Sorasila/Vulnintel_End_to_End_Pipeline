# S1: PostgreSQL connector (CDC) จาก Neon และแผนสำรอง snapshot

> คำเตือน: ห้ามวาง secret, token, API key หรือ password ลงในไฟล์นี้ (รวมถึงใน output/screenshot) ให้ mask ก่อนเสมอ (โดยเฉพาะ `NEON_DATABASE_URL` และ password ของ role `databricks_replication`)

## คำถาม

Lakeflow Connect PostgreSQL connector สร้าง gateway และ ingest จาก Neon พร้อม SCD2 ได้บน Databricks Free Edition ไหม ถ้าไม่ได้ แผนสำรอง snapshot (Neon → CSV ใน UC Volume → Auto Loader → `dp.create_auto_cdc_from_snapshot_flow` SCD2) ใช้ได้จริงไหม

**ผ่าน:** ส่วน A (CDC) ผ่าน (ตรวจ SCD2 ได้ครบ) และ gateway ใช้ compute ไม่เกินโควตา → ใช้ CDC ตาม design (Phase 4 ทาง A)
**ไม่ผ่าน:** ส่วน A ไม่ผ่านหรือ connector ไม่มีให้ใช้ แล้วส่วน B (snapshot) ผ่าน → ใช้ snapshot (Phase 4 ทาง B) ข้อดีคือหมดปัญหา Neon ลบ replication slot หลัง 40 ชั่วโมง ให้ลบ slot และ publication ใน Neon หลังจบ spike

เกณฑ์ผ่านของส่วน B: หลัง `seed` มี 10 แถว current และหลัง `mutate` แถวที่แก้ 2 แถวมี 2 เวอร์ชัน, แถวที่ลบถูกปิด `__END_AT`, แถวใหม่ 1 แถว และ current รวม 10 แถว (job รายงาน `scd2_ok=True`)

## setup

- Databricks Free Edition (ดู `_environment.md`), serverless เท่านั้น, catalog `vulnintel_dev`, volume `ops.landing` และ `ops._checkpoints` (สร้างใน S2 แล้ว)
- Neon: project `vulnintel-cmdb`, AWS us-east-2, Postgres 17, ยังไม่เปิด logical replication (ตอนเริ่ม spike)
- Auth จาก GitHub Actions: service principal OAuth M2M เหมือน S2
- GitHub Secret ใหม่: `NEON_DATABASE_URL` (ดูส่วน B ข้อ 1)
- โค้ด (ใช้แล้วทิ้ง):
  - `seeds/sql/cmdb_schema.sql`: ตาราง `assets` และ `asset_software` (`asset_id` ไม่มี NOT NULL/UNIQUE โดยตั้งใจ, `REPLICA IDENTITY DEFAULT`, รันซ้ำได้)
  - `spikes/s1/neon_setup.sql`: role `databricks_replication`, GRANT, publication `databricks_publication`, slot `databricks_slot` (**รันเฉพาะเมื่อ connector มีให้ใช้**)
  - `spikes/s1/neon_cmdb.py` (psycopg 3): `seed` (apply schema + insert 10 แถวต่อตาราง ถ้าว่าง), `mutate` (update 2 แถว id 2 และ 5 ตั้ง `environment='dr'` + bump `updated_at`, delete id 8, insert 1 แถวใหม่), `reset` (TRUNCATE … RESTART IDENTITY)
  - `spikes/s1/snapshot_upload.py`: dump `assets` เป็น CSV (header, ทุกค่าเป็น text) แล้ว upload ด้วย Files API `overwrite=False` ไปที่ `/Volumes/vulnintel_dev/ops/landing/cmdb_assets/YYYY/MM/DD/cmdb_assets_<run_id>-<attempt>_0.csv`
  - `spikes/s1/snapshot_ingest.py`: Auto Loader (`csv`, `header=true`, `inferColumnTypes=false`, `addNewColumns`, `_rescued_data`) → `vulnintel_dev.bronze.cmdb_assets_snapshot` พร้อมคอลัมน์ metadata, `_load_dttm` และ `snapshot_id = run_id * 100 + attempt` (แปลงจากชื่อไฟล์) checkpoint `/Volumes/vulnintel_dev/ops/_checkpoints/cmdb_assets_snapshot`
  - `spikes/s1/snapshot_fallback_pipeline.py`: SDP pipeline → `vulnintel_dev.silver.spike_dim_asset` ด้วย `dp.create_auto_cdc_from_snapshot_flow(keys=["id"], stored_as_scd_type=2)` โดย `next_snapshot(latest_version)` เลือก `snapshot_id` ที่เล็กที่สุดที่มากกว่า `latest_version` (หรือเล็กที่สุดเมื่อเป็น `None`) และตัดคอลัมน์ metadata ของ bronze ออกก่อนส่งเข้า SCD2
  - `spikes/s1/report.py`: RESULT lines ของ bronze/silver เขียนลง `vulnintel_dev.ops.spike_s1_results` (`run_id`, `case_name`, `line`, `ts`) ด้วย `spikes/s1/fetch_results.py` ดึงมาแสดงใน Job summary
  - `spikes/s1/databricks.yml`: bundle `vulnintel-spike-s1` มี pipeline serverless และ 3 job: `spike_s1_snapshot` (ingest → pipeline `full_refresh: false` → report, ใช้กับ `mutate`), `spike_s1_snapshot_full` (เหมือนกันแต่ `full_refresh: true`, ใช้กับ `seed`) และ `spike_s1_reset`
  - `.github/workflows/spike-s1.yml`: `workflow_dispatch` input `case` = `seed` | `mutate` | `reset`, `concurrency: databricks-pipelines`, `timeout-minutes: 20`
- ผลการตรวจ signature ใน docs.databricks.com: `create_auto_cdc_from_snapshot_flow(target, source, keys, stored_as_scd_type="1", track_history_column_list=None, track_history_except_column_list=None, once=False)`; `source` เป็นชื่อตาราง/view หรือ callable `latest_version -> (DataFrame, version) | None`; ถ้าเรียกครั้งแรกแล้วคืน `None` pipeline update จะล้ม (ดังนั้น bronze ต้องมีข้อมูลก่อนรัน pipeline) docs ใช้ค่า default เป็น string `"1"` แต่ spike เขียน `stored_as_scd_type=2` เป็น int ตาม brief ถ้า pipeline ปฏิเสธ ให้เปลี่ยนเป็น `"2"` แล้วบันทึกไว้ที่นี่

## ขั้นตอนที่ทำจริง

### ส่วน A: CDC ด้วย Lakeflow Connect (ทำใน UI โดย [คุณ] ใช้เวลาไม่เกิน 2 ชั่วโมง)

ทำตามลำดับ และ **หยุดที่ข้อ 1 ถ้า connector ไม่มีให้ใช้** (ยังไม่แตะ Neon เลย เพราะข้อ 2 เปลี่ยนกลับไม่ได้) แล้วข้ามไปส่วน B

1. ตรวจว่า connector มีให้ใช้ไหม: Databricks → **Data ingestion** (แถบซ้าย) → ดูว่ามีการ์ด **PostgreSQL** ไหม ถ้าไม่มี ให้ดู **Settings → Previews** (ตรงกับชื่อ "Lakeflow Connect" หรือ "PostgreSQL") ว่ามี preview ให้เปิดไหม แล้วกลับมาที่ Data ingestion อีกครั้ง บันทึกผล (มี/ไม่มี/ต้องเปิด preview) พร้อม screenshot
2. (เฉพาะถ้ามี) เปิด logical replication ใน Neon: Neon console → project `vulnintel-cmdb` → **Settings → Logical Replication → Enable** **คำเตือน: เปลี่ยนกลับไม่ได้** และ compute จะ restart จากนั้นรัน `SHOW wal_level;` ต้องได้ `logical`
3. ให้ตารางมีข้อมูล: กด Run workflow `spike-s1` ด้วย `seed` (ต้องเพิ่ม secret `NEON_DATABASE_URL` ก่อน ดูส่วน B ข้อ 1) ซึ่งสร้างตารางและ 10 แถว (run นี้รันเส้นทาง snapshot ของส่วน B ด้วย ไม่เป็นอะไร)
4. รัน `spikes/s1/neon_setup.sql` ส่วน A ด้วย owner role (แทน `<CHOOSE_A_STRONG_PASSWORD>` ตอนรัน ห้าม commit) แล้วส่วน B ด้วย role `databricks_replication` (สร้าง slot) ตรวจ `pg_replication_slots` และ `pg_publication`
5. สร้าง UC connection: Databricks → **Catalog → Connections → Create connection** (หรือจากหน้า Data ingestion → PostgreSQL) ประเภท PostgreSQL, host แบบ **direct** (ไม่มี `-pooler` ใน hostname), port `5432`, user `databricks_replication`, database `neondb` (หรือชื่อที่ใช้จริง), SSL require
6. สร้าง ingestion pipeline: เลือก connection ข้างต้น, ตาราง `public.assets` และ `public.asset_software`, publication `databricks_publication`, slot `databricks_slot`, destination catalog `vulnintel_dev` schema `bronze`, โหมด **Change data capture** และเปิด **SCD type 2** บันทึก **error หรือ compute ที่ gateway ขอใช้แบบคำต่อคำ** (ข้อความเต็มและ screenshot) ถ้า gateway ไม่ start จบส่วน A ที่นี่ แล้วทำส่วน B
7. ถ้า gateway รันได้: กด Run workflow `mutate` (update 2 แถว, delete 1, insert 1 ใน Neon; ขั้นตอน upload/ingest ของ snapshot ใน run นี้ไม่เกี่ยวกับ connector และไม่เป็นอะไร) แล้ว trigger ingestion pipeline ตรวจใน SQL editor (แก้ `<schema>` ให้ตรงกับ destination จริง):

```sql
-- ทุกแถวประวัติ: ต้องมี __START_AT, __END_AT
SELECT id, asset_id, environment, updated_at, __START_AT, __END_AT
FROM vulnintel_dev.<schema>.assets ORDER BY id, __START_AT;

-- id ที่มากกว่า 1 เวอร์ชัน: คาดหวัง 2 id (id 2 และ 5)
SELECT id, count(*) AS versions FROM vulnintel_dev.<schema>.assets GROUP BY id HAVING count(*) > 1 ORDER BY id;

-- แถวที่ถูกลบ: คาดหวัง id 8 และ __END_AT ไม่ว่าง
SELECT id, __END_AT FROM vulnintel_dev.<schema>.assets WHERE id = 8;

-- แถว current: คาดหวัง 10 แถว (10 - 1 ลบ + 1 เพิ่ม) และมี id 11
SELECT count(*), max(id) FROM vulnintel_dev.<schema>.assets WHERE __END_AT IS NULL;
```

   ถ้าจะทำส่วน B ต่อหลังข้อนี้ ให้รัน `case = reset` ก่อน เพื่อให้ `mutate` ในส่วน B เริ่มจากข้อมูล seed ใหม่

   ถ้า connector ไม่สร้างคอลัมน์ชื่อ `__START_AT`/`__END_AT` ให้บันทึกชื่อคอลัมน์จริง
8. วัด compute ที่ gateway ใช้ใน 24 ชั่วโมงเทียบโควตา (Settings → Usage หรือหน้า compute ของ pipeline) และดูว่า gateway นับเป็น active pipeline ไหม (ตัวเลขนี้ใช้ใน S3 ที่จำกัด concurrent pipeline)
9. **Cleanup ใน Neon หลังจบ spike (ทั้งผ่านและไม่ผ่าน ถ้าเคยสร้าง slot):** หยุด/ลบ ingestion pipeline และ gateway ก่อน แล้วรัน `SELECT pg_drop_replication_slot('databricks_slot'); DROP PUBLICATION databricks_publication;` (ดูส่วนท้ายของ `neon_setup.sql`) slot ที่ไม่มีคนอ่านจะสะสม WAL ทำให้เต็มโควตาของ Neon

### ส่วน B: แผนสำรอง snapshot (ทำเมื่อส่วน A ไม่ผ่านหรือ connector ไม่มี ใช้เวลาไม่เกิน 3 ชั่วโมง)

1. เพิ่ม GitHub Secret `NEON_DATABASE_URL`: Neon console → project `vulnintel-cmdb` → **Connect** → เลือก **direct connection** (ปิด Connection pooling) → คัดลอก connection string ที่เป็น `postgresql://…?sslmode=require` → GitHub repo → Settings → Secrets and variables → Actions → New repository secret ห้ามวางค่าลงในไฟล์นี้หรือ chat
2. GitHub → Actions → **spike-s1** → Run workflow `case = seed` (กด Run workflow ใหม่เสมอ อย่าใช้ "Re-run jobs") รอจบ
3. Run workflow `case = mutate` รอจบ ห้ามรัน `mutate` ซ้ำโดยไม่ `reset` (รอบซ้ำจะ bump `updated_at` อีกและ insert แถวเพิ่ม ผล check จะไม่ตรง)
4. เริ่มใหม่: `case = reset` (TRUNCATE ตารางใน Neon, drop bronze table, ลบ checkpoint และไฟล์ CSV ใน landing) แล้ว `seed` ใหม่ จะ full refresh pipeline ให้เอง ดูหมายเหตุด้านล่าง

ผลทั้งหมดอยู่ใน Job summary ของ run (หัวข้อ "neon output", "upload output", "deploy output", "bundle_run output" และ "spike-s1 results") ก๊อปไปวางในหัวข้อหลักฐานได้เลย

หมายเหตุการออกแบบ (เลือกแล้ว):
- `seed` รัน job `spike_s1_snapshot_full` (pipeline `full_refresh: true`) ส่วน `mutate` รัน job ที่ `full_refresh: false` เพราะ `full_refresh` ของ `pipeline_task` เป็นค่าคงที่ใน bundle ไม่รับ parameter `reset` ไม่ drop ตาราง silver ที่ pipeline เป็นเจ้าของ (drop ตรงๆ อาจถูกปฏิเสธ) แต่ `seed` ถัดไป full refresh ที่ล้าง silver และสถานะ `latest_version` ของ flow แล้วสร้างจาก bronze ใหม่ (ถ้าไม่ full refresh เวอร์ชันเก่าจะค้างอยู่) การเรียก full refresh ตอน bronze ว่างไม่เกิดขึ้น เพราะ task `ingest` รันก่อน `pipeline` เสมอ (ถ้า `next_snapshot` คืน `None` ในครั้งแรก update จะล้ม)
- `snapshot_id` = `GITHUB_RUN_ID * 100 + GITHUB_RUN_ATTEMPT` (brief ระบุแค่ run id) เพื่อให้ "Re-run jobs" ที่ใช้ run id เดิมไม่สร้าง snapshot_id ซ้ำ (ซึ่งจะทำให้ `next_snapshot` ได้ 2 ไฟล์ใน snapshot เดียวและ key ซ้ำ)
- `updated_at` ของ seed ถูกกำหนดค่าคงที่ (ไม่ใช้ `now()`) เพื่อให้แถวที่ไม่ถูกแก้ดูเหมือนเดิมทุกคอลัมน์ใน snapshot รอบสอง และไม่เกิดเวอร์ชันใหม่โดยไม่จำเป็น

### ผลที่คาดหวังต่อ case (ส่วน B)

| case | สิ่งที่เกิดใน Neon / Volume | RESULT ที่คาดหวัง |
|---|---|---|
| `seed` | สร้างตาราง + 10 แถวต่อตาราง, upload CSV 10 แถว | `[bronze] snapshots=1`, `snapshot_id=… rows=10`; `[silver] total_rows=10`, `current_rows=10`, `ids_with_multiple_versions=0`, `ids_deleted=0`, `scd2_ok=True` |
| `mutate` | update id 2 และ 5, delete id 8, insert id 11, upload CSV 10 แถว | `[bronze] snapshots=2` (10 + 10 แถว); `[silver] total_rows=13`, `current_rows=10`, `ids_with_multiple_versions=2 [(2, 2), (5, 2)]`, `ids_deleted=1 [8]`, `scd2_ok=True` และคอลัมน์ `__START_AT`/`__END_AT` ปรากฏในรายการ columns |
| `reset` | TRUNCATE ใน Neon, ล้าง bronze/checkpoint/landing | `reset: done` |

ถ้า job ล้มที่ task `pipeline` task `report` ยังรัน (`run_if: ALL_DONE`) และรายงานว่า silver ไม่มี หรือ error ของ pipeline ดูได้ที่ปุ่มของ pipeline update ใน Databricks (บันทึก error แบบคำต่อคำ)
