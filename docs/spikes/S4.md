# S4: Auth จาก GitHub Actions ไป Databricks (S4a) และ GCP (S4b)

> คำเตือน: ห้ามวาง secret, token, API key หรือ password ลงในไฟล์นี้ (รวมถึงใน output/screenshot) ให้ mask ก่อนเสมอ

## S4a (Databricks)

### คำถาม

GitHub Actions ยืนยันตัวตนกับ Databricks Free Edition workspace ด้วย service principal OAuth (M2M) ได้ไหม ถ้าไม่ได้ PAT มีข้อจำกัดอะไร

เกณฑ์:

- **ผ่าน:** ทั้ง 4 check (`current_user.me`, `files.upload`, `sql.select_1`, `jobs.list`) สำเร็จด้วย OAuth M2M → ใช้ service principal และตั้ง `run_as` ของ bundle เป็น SP
- **ไม่ผ่าน:** ใช้ PAT, เพิ่มงาน "ต่ออายุ PAT" ใน runbook และให้ workflow keepalive เตือนก่อน PAT หมดอายุ 14 วัน

### setup

- Workspace: Databricks Free Edition, host `dbc-9895c944-aa73.cloud.databricks.com` (ดู `_environment.md`), serverless เท่านั้น
- โค้ด: `spikes/s4/dbx_auth_check.py`, workflow `.github/workflows/spike-s4a.yml` (`workflow_dispatch`, input `auth_type` = `oauth` | `pat`)
- SQL setup: `spikes/s2/setup.sql` (catalog `vulnintel_dev`, volume `landing`)
- GitHub Secrets: `DATABRICKS_HOST` (`https://dbc-9895c944-aa73.cloud.databricks.com`), `DATABRICKS_CLIENT_ID`, `DATABRICKS_CLIENT_SECRET`; สำหรับ PAT: `DATABRICKS_TOKEN`
- GitHub Variable (ไม่บังคับ): `DATABRICKS_WAREHOUSE_ID` (ถ้าไม่ตั้ง script ใช้ warehouse แรกจาก `warehouses.list()`)

### ผล (ผ่าน/ไม่ผ่าน/บางส่วน)

**ผ่าน** (23 ต.ค. 2026) Free Edition รองรับ service principal OAuth M2M จาก GitHub Actions ครบทั้ง `current_user.me`, Files API upload เข้า UC Volume, SQL warehouse และ Jobs API ต่างจากรายงานใน community ที่ว่า Free Edition ใช้ไม่ได้

### ผลต่อ design

- ใช้ service principal `vulnintel-ci` (OAuth M2M) สำหรับทุก workflow และตั้ง `run_as` ของ bundle เป็น SP ไม่ต้องมีงานต่ออายุ PAT
- ตอนสร้าง OAuth secret ต้องเลือก Scope **Other APIs** และให้มี `all-apis` (หรือกำหนด `Config(scopes=[...])` ให้ตรงกับ secret) จดไว้ใน runbook
- OAuth secret มีวันหมดอายุ: เพิ่มงาน rotate secret ใน runbook และให้ keepalive เตือนก่อนหมดอายุ
- สิทธิ์ที่ SP ต้องมี: entitlement Workspace access + Databricks SQL access, `USE CATALOG, USE SCHEMA, READ VOLUME, WRITE VOLUME, SELECT, MODIFY, CREATE TABLE` บน catalog และ CAN USE บน SQL warehouse

### เวลาที่ใช้

ราว 30 นาทีของการตั้งค่าจริง (16:00-16:25 น. UTC 23 ต.ค.) อยู่ใน time-box 3 ชั่วโมง

## S4b (GCP)

### คำถาม

GitHub Actions ใช้ Workload Identity Federation (OIDC, ไม่มี service account key) load ข้อมูลเข้า BigQuery sandbox ได้ไหม และ `WRITE_TRUNCATE` reset วันหมดอายุ (`expires`, 60 วันของ sandbox) ของตารางหรือไม่

เกณฑ์:

- **ผ่าน:** WIF load Parquet สำเร็จ → ใช้ OIDC ไม่เก็บ key ผลของการทดสอบ `expires` กำหนดวิธี export ใน Task 6.1 (load ทับด้วย `WRITE_TRUNCATE` อย่างเดียว, เลื่อน `expires` เอง หรือ `delete_table` แล้วสร้างใหม่)
- **ไม่ผ่าน:** ใช้ service account key (secret `GCP_SA_KEY`) และเพิ่มงาน rotate key ใน runbook (ดู "Fallback" ด้านล่าง)

### setup

- GCP project: `custom-dominion-472909-u5` ไม่ผูก billing (BigQuery sandbox: ตารางหมดอายุใน 60 วัน) dataset `vulnintel_spike` อยู่ที่ `US` multi-region
- โค้ด: `spikes/s4/gcp_setup.sh` (รันใน Cloud Shell), `spikes/s4/bq_load_check.py`, workflow `.github/workflows/spike-s4b.yml` (`workflow_dispatch`, input `mode` = `load` | `extend_expiry` | `recreate`)
- Service account `vulnintel-export` มี `roles/bigquery.jobUser` (project) และ `roles/bigquery.dataEditor` (dataset `vulnintel_spike`)
- Workload identity pool `github` + provider `github-oidc` (issuer `https://token.actions.githubusercontent.com`) ใช้ attribute condition `assertion.repository_id == '<REPO_ID>' && assertion.ref == 'refs/heads/main'` (ใช้ `repository_id` ไม่ใช่ชื่อ repo เพราะชื่อเปลี่ยนหรือต่างตัวพิมพ์ได้) และ bind `roles/iam.workloadIdentityUser` ให้ `principalSet://.../attribute.repository_id/<REPO_ID>` เท่านั้น
- เพราะ condition ยอมเฉพาะ `refs/heads/main` ต้อง merge workflow เข้า main ก่อน แล้วค่อยกด "Run workflow" จาก main
- GitHub Variables (ไม่ใช่ Secrets เพราะไม่ใช่ความลับ): `GCP_WIF_PROVIDER`, `GCP_SA_EMAIL`, `GCP_PROJECT_ID`
- เวอร์ชันที่ pin ใน workflow: `google-cloud-bigquery~=3.46.0`, `pyarrow~=26.0.0` (Python 3.12), `google-github-actions/auth@v2`

   - (ก) `mode=extend_expiry`: หลัง load เรียก `update_table(["expires"])` เลื่อน `expires` ไปอีก 1 วันจากค่าปัจจุบัน (เป็นการเลื่อนจริง ไม่ใช่การย่อ) วิธีอ่านผล: `extend_original` = expires ก่อนเลื่อน, `extend_target` = ค่าที่ขอ, `extended.expires` = ค่าที่ BigQuery ส่งกลับ, `extend_delta_seconds` = `extended.expires - extend_original` (ยอมเลื่อนเต็ม = 86400), `extend_capped=True` แปลว่า sandbox รับคำสั่งแต่ปรับค่ากลับ (เช่น cap ที่ 60 วัน), `extend_expiry=REFUSED <class>: <message>` แปลว่า sandbox ปฏิเสธ (`Forbidden`/`BadRequest`/`PermissionDenied`) ส่วน `ERROR ...` แปลว่าล้มด้วยเหตุอื่นและ run จะเป็นสีแดง ไม่ใช่ผลของ sandbox

### ผล (ผ่าน/ไม่ผ่าน/บางส่วน)

**ผ่าน**
1. WIF: GitHub Actions (จาก `main`) ได้ token ของ SA `vulnintel-export` ผ่าน OIDC และ load เข้า BigQuery sandbox ได้ ไม่ต้องใช้ SA key
2. `WRITE_TRUNCATE` **ไม่ reset** `expires` (และไม่เปลี่ยน `created`) ตารางจึงหมดอายุ 60 วันหลังสร้างครั้งแรก แม้จะ load ทุกวัน
3. sandbox ยอมทั้งสองทาง: (ก) `update_table(["expires"])` เลื่อนได้จริงและไม่ถูก cap แม้ค่าใหม่จะเกิน 60 วันนับจากตอนนี้ (60.939 วัน) (ข) `delete_table` แล้ว load ใหม่ ได้ `expires` = now + 60 วัน

### ผลต่อ design

1. Auth GCP: ใช้ OIDC/WIF (provider ผูก `repository_id` + `refs/heads/main`) ไม่ใช้ SA key workflow ที่ export ต้องรันจาก `main` เท่านั้น
2.
