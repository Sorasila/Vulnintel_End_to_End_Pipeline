# S2: Files API upload + Auto Loader บน serverless

> คำเตือน: ห้ามวาง secret, token, API key หรือ password ลงในไฟล์นี้ (รวมถึงใน output/screenshot) ให้ mask ก่อนเสมอ

## คำถาม

GitHub Actions upload NDJSON เข้า UC Volume ผ่าน Files API ได้ไหม และ Auto Loader `availableNow` บน Databricks Free Edition (serverless) อ่านเข้า bronze ได้ตามกฎของ BronzeIngestor ทุกข้อไหม

**ผ่าน:** กรณี 1-4 ผ่าน → ใช้ตาม design ถ้ากรณี 5 (`cleanSource`) ผ่านด้วย ให้ใช้ `cloudFiles.cleanSource` แทน job ลบไฟล์รายสัปดาห์
**ไม่ผ่าน:** ใช้ Google Drive connector เป็น landing แทน (แผนสำรองใน spec) และเขียน spike ย่อยของทางนั้น

## setup

- Workspace: Databricks Free Edition, host ดู `_environment.md`, serverless เท่านั้น
- Step 1 (สร้าง catalog/schema/volume) **ทำเสร็จแล้วโดยคุณ** จาก `spikes/s2/setup.sql`: catalog `vulnintel_dev`, schema `bronze`/`silver`/`gold`/`ops`, volume `vulnintel_dev.ops.landing` และ `vulnintel_dev.ops._checkpoints` ชื่อที่ขึ้นต้นด้วย `_` **ถูกรับ** จึงไม่ต้องใช้ชื่อสำรอง `checkpoints`
- Auth: service principal OAuth M2M (ผ่านใน S4a) GitHub Secrets `DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID`, `DATABRICKS_CLIENT_SECRET` และ env `DATABRICKS_AUTH_TYPE=oauth-m2m`
- โค้ด (ใช้แล้วทิ้ง):
  - `.github/workflows/spike-s2.yml`: `workflow_dispatch` input `case` (`initial` | `rerun` | `new_column` | `clean_source` | `reset`), `concurrency: databricks-pipelines`, `timeout-minutes: 20`
  - `spikes/s2/upload_fixtures.py`: สร้าง NDJSON deterministic (field `cve_id`, `score`, `date` เป็น string ทั้งหมด) upload ด้วย `WorkspaceClient().files.upload(path, f, overwrite=False)` ไปที่ `/Volumes/vulnintel_dev/ops/landing/spike/YYYY/MM/DD/spike_<run_id>-<attempt>_<part>.json` (วันที่ UTC) แล้วพิมพ์เวลาที่ใช้ กรณี `initial` ลอง upload path แรกซ้ำเพื่อดู error
  - `spikes/s2/databricks.yml`: Databricks Asset Bundle `vulnintel-spike-s2` (target `dev`) มี job `spike_s2_autoloader` 1 task (`spark_python_task` → `autoloader_probe.py`) บน serverless (`environments`, `environment_version: "4"`), `max_retries: 1`, job parameters `case` และ `run_id`
  - `spikes/s2/autoloader_probe.py`: Auto Loader → `vulnintel_dev.bronze.spike_raw`, checkpoint `/Volumes/vulnintel_dev/ops/_checkpoints/spike_raw`, schema location `.../spike_raw/_schema` แล้วเขียน RESULT lines ลงตาราง `vulnintel_dev.ops.spike_s2_results` (คอลัมน์ `run_id`, `case_name`, `line`, `ts`)
  - `spikes/s2/fetch_results.py`: step สุดท้ายของ workflow ดึง RESULT lines จากตารางนั้นผ่าน SQL warehouse มาแสดงใน Job summary
- Options ของ Auto Loader: `cloudFiles.format=json`, `cloudFiles.inferColumnTypes=false`, `cloudFiles.schemaEvolutionMode=addNewColumns`, `rescuedDataColumn=_rescued_data`, `cloudFiles.schemaLocation=...` เพิ่ม `_load_dttm`, `_file_path`, `_filename`, `_file_size`, `_file_modification_time` (จาก `_metadata`) และไม่มีคอลัมน์ชื่อ `_metadata` เขียนด้วย `outputMode("append")`, `mergeSchema=true`, `trigger(availableNow=True)`

## ขั้นตอนที่ทำจริง

ลำดับที่ [คุณ] รัน ทุกครั้งให้กด "Run workflow" ใหม่ (อย่าใช้ "Re-run jobs") เลือก `case` ตามลำดับนี้ และรอให้จบก่อนรัน case ถัดไป:

1. `initial`
2. `rerun`
3. `new_column`
4. `clean_source`

ผลทั้งหมดอยู่ใน Job summary ของ run (หัวข้อ "upload output" (เวลา upload, path, exception ของ upload ซ้ำ), "deploy output" (error ของ `bundle deploy` เช่น environment_version ถูกปฏิเสธ), "bundle_run output" และ "spike-s2 results") ก๊อปมาวางในหัวข้อหลักฐานได้เลย ไม่ต้องดาวน์โหลด log

กรณี `reset` (ไม่ได้อยู่ในลำดับด้านบน): drop `vulnintel_dev.bronze.spike_raw`, ลบ checkpoint dir และลบ fixture ใน `landing/spike/<YYYY>/` เพื่อเริ่ม spike ใหม่ตั้งแต่ `initial` (ไม่แตะไฟล์อื่นเช่น `auth_check_*.txt` ของ S4a และไม่ลบตาราง results)

### ผลที่คาดหวังต่อ case

| case | สิ่งที่ upload | ผลที่คาดหวัง |
|---|---|---|
| `initial` | 3 ไฟล์ x 100 แถว (+ ลอง upload path ซ้ำ 1 ครั้ง) | job SUCCESS, `rows_added=300`, `total_rows=300`, ทุกคอลัมน์ที่ไม่ใช่ metadata เป็น `string` (`all_non_metadata_columns_string=True`), `has_vendor=False` และ upload ซ้ำ error เพราะ `overwrite=False` |
| `rerun` | ไม่ upload | job SUCCESS, `rows_added=0`, `total_rows=300` |
| `new_column` | 1 ไฟล์ x 100 แถว มี field `vendor` | attempt 0: `stream=FAILED` (schema เปลี่ยน, เช่น `UnknownFieldException`) จากนั้น retry (attempt 1): `stream=SUCCESS` → job สุดท้าย SUCCESS, `has_vendor=True`, `rows_added=100`, `total_rows=400` |
| `clean_source` | 1 ไฟล์ x 10 แถว | `cleanSource.accepted=True` (รับ `DELETE` + `retentionDuration=30 days`) หรือ `cleanSource.accepted=False` พร้อม error ที่บอกว่า serverless ไม่รองรับตรงไหน |
| `reset` | ไม่ upload | `reset: done` |

หมายเหตุ: ผลของ `new_column` คือกรณี 3 และ 4 ของ brief รวมกัน (ตั้ง `max_retries=1` ใน bundle ตั้งแต่ต้น จึงเห็นทั้ง "attempt แรก fail" และ "retry ผ่าน" ใน run เดียว) ถ้าอยากดูกรณีที่ 4 แยกด้วย field `product` ต้องแก้ `upload_fixtures.py` ให้เพิ่ม field นั้น (ไม่ได้ทำใน spike นี้)

ผลที่ลองแล้วไม่ work: ไม่มี ทั้ง 4 case รันผ่านในรอบแรก (23 ต.ค. 2026)

## ผล (ผ่าน/ไม่ผ่าน/บางส่วน)

**ผ่าน** ทุก case: Files API upload จาก GitHub Actions, Auto Loader `availableNow` บน serverless ได้ทุกคอลัมน์เป็น string, รันซ้ำไม่อ่านไฟล์เดิม, คอลัมน์ใหม่ทำให้ stream หยุดหนึ่งครั้งแล้ว retry ผ่านพร้อมคอลัมน์ใหม่ และ `cleanSource` ใช้ได้บน serverless ไม่ต้องใช้ Google Drive connector

## ผลต่อ design

- ใช้ landing แบบ UC Volume + Files API + Auto Loader ตาม design
- ใช้ `cloudFiles.cleanSource=DELETE` กับ `retentionDuration=30 days` แทน job ลบไฟล์รายสัปดาห์ (ตัด `volume-retention.yml` และ `delete_older_than` ใน Task 3.1/6.3 ออก) แต่ยังต้องยืนยันว่าไฟล์ถูกลบจริงหลัง 30 วันระหว่าง burn-in
- `max_retries: 1` ของ bronze task พอสำหรับ schema evolution แบบ `addNewColumns` (fail หนึ่งครั้งแล้วผ่าน)
- Task 1.1 pin `pyspark==4.2.*` และ Python 3.12; serverless `environment_version: "4"`
- `overwrite=False` ทำให้ upload path ซ้ำ fail ด้วย `AlreadyExists` extract ต้องใช้ชื่อไฟล์ที่ไม่ซ้ำต่อ run attempt (ใส่ `GITHUB_RUN_ATTEMPT` ด้วย)
- probe อ่านเลข attempt ของ task ไม่ได้ (`attempt=None`) ถ้าต้องใช้ใน production ให้ส่ง `{{task.run_id}}` เป็น parameter แทน
