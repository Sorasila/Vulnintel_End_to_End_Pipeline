# S3: ข้อจำกัด 1 active pipeline ต่อประเภท

> คำเตือน: ห้ามวาง secret, token, API key หรือ password ลงในไฟล์นี้ (รวมถึงใน output/screenshot) ให้ mask ก่อนเสมอ (โดยเฉพาะ host ของ workspace ใน URL)

## คำถาม

เมื่อสั่ง pipeline 2 ตัวพร้อมกัน (เช่น dev กับ prod หรือ ingestion กับ ETL) ระบบ queue, reject หรือรันพร้อมกัน และ job ที่มี pipeline task ต่อกันเป็นลำดับ (`spike_s3_a` → `spike_s3_b`) รันได้ปกติไหม รวมถึงเกิดอะไรขึ้นเมื่อสั่ง job ระหว่างที่ pipeline ตัวแรกของ job ถูกสั่งรันแยกอยู่

**ผ่าน:** Step 3 สำเร็จทั้ง 2 task และได้พฤติกรรมของ Step 2 กับ Step 4 ที่บันทึกแบบคำต่อคำ (queue / reject พร้อม error message / รันซ้อน / job รอ-fail-retry) พอจะตัดสินนโยบายของ workflow ได้ spike นี้เป็นการสังเกต ไม่มีผลลัพธ์ "ล้ม" ของ Step 2 และ Step 4 (reject หรือ queue ก็ถือว่าได้คำตอบ)

## setup

- Databricks Free Edition (ดู `_environment.md`), serverless เท่านั้น, catalog `vulnintel_dev`, schema `ops` (สร้างใน S2 แล้ว)
- Auth จาก GitHub Actions: service principal OAuth M2M เหมือน S2/S1 (secrets `DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID`, `DATABRICKS_CLIENT_SECRET`) ไม่ต้องเพิ่ม secret ใหม่
- โค้ด (ใช้แล้วทิ้ง):
  - `spikes/s3/databricks.yml`: bundle `vulnintel-spike-s3` มี pipeline serverless 2 ตัว (`spike_s3_a`, `spike_s3_b`, `continuous: false`, `development: true`) แต่ละตัวมี materialized view เดียวที่ `spark.range(1000)` และ job `spike_s3_seq` (`run_a` → `run_b`, `timeout_seconds: 900`) task ที่เป็น pipeline ตั้ง `max_retries: 1` และ `min_retry_interval_millis: 60000` เพื่อดูว่า retry ช่วยได้ไหมใน Step 4
  - `spikes/s3/pipeline_a.py`, `spikes/s3/pipeline_b.py`: `@dp.materialized_view` (`from pyspark import pipelines as dp`) ตัวละ 1 view
  - `spikes/s3/probe.py`: รันบน GitHub runner ด้วย Databricks SDK หา pipeline/job จากชื่อ แล้วทำ Step 2-4 พิมพ์ผลเป็นบรรทัด `RESULT ...` SDK ตั้ง timeout ในโค้ด (`http_timeout_seconds=20`, `retry_timeout_seconds=30`) ทุก loop มี deadline (รอ pipeline ว่างก่อนเริ่ม 300 วินาที, รอ pipeline 600 วินาที, รอ job 960 วินาที, งบรวม 35 นาที) และตอนจบ (หรือเมื่อถูก cancel) จะ stop pipeline และ cancel job run ที่ยังค้าง
  - `.github/workflows/spike-s3.yml`: `workflow_dispatch` input `case` = `all` | `parallel` | `seq` | `seq_during` | `destroy`, `concurrency: databricks-pipelines`, `timeout-minutes: 50` (step probe 40 นาที)
- **ข้าม Step 5 ของแผน** (ทดสอบ ingestion pipeline/gateway ของ CDC) เพราะผล S1 ยืนยันว่า Lakeflow Connect CDC ใช้ไม่ได้บน Free Edition (ตัวเลือก Change data capture ถูก disable) ทาง B (snapshot) ไม่มี ingestion pipeline หรือ gateway จึงไม่มีอะไรให้ทดสอบเพิ่ม

## ขั้นตอนที่ทำจริง

### วิธีรัน

1. GitHub → Actions → **spike-s3** → Run workflow `case = all` (กด Run workflow ใหม่เสมอ อย่าใช้ "Re-run jobs") ใช้เวลาประมาณ 15-25 นาที
2. workflow ทำตามลำดับ: deploy bundle → `probe.py` (Step 2 → 3 → 4) → สรุปลง Job summary (หัวข้อ "probe RESULT lines" และ "deploy output")
3. ถ่าย screenshot Job summary (หรือก๊อปบรรทัด `RESULT`) ไปวางในหัวข้อหลักฐาน ถ้าต้องรันซ้อมเฉพาะบาง step ให้เลือก `case = parallel`, `seq` หรือ `seq_during`
4. เมื่อจบ Gate G0 ให้รัน `case = destroy` เพื่อลบ pipeline, job และ materialized view ของ spike ออก (`databricks bundle destroy -t dev --auto-approve`)

### สิ่งที่ probe ทำในแต่ละ step

| step | case | สิ่งที่ทำ |
|---|---|---|
| 2 | `parallel` | รอให้ A และ B ว่างก่อน แล้ว `pipelines.start_update` ของ A และ B พร้อมกัน (2 thread, ห่างกันไม่เกิน ~1 วินาที) บันทึกต่อ pipeline: `start_update` raise หรือไม่ (ชื่อ exception และข้อความ truncate ~300 ตัวอักษร), `update_id`, state ของ update จาก `get_update` ทุก 5 วินาทีเป็น timeline เวลาสัมพัทธ์, state สุดท้าย และ ERROR event ของ pipeline ถ้า update ไม่ COMPLETED แล้วตัดสิน verdict จากช่วงที่ state = `RUNNING` ของทั้งสองตัว |
| 3 | `seq` | `jobs.run_now(spike_s3_seq)` แล้ว poll `get_run` ทุก 5 วินาที บันทึก state/result ของแต่ละ task, attempt, เวลา และ `seq_ok` (ต้อง SUCCESS ทั้ง `run_a` และ `run_b`) |
| 4 | `seq_during` | `start_update(spike_s3_a)` แล้ว `run_now(spike_s3_seq)` ทันที (ห่างไม่เกิน ~2 วินาที) บันทึก timeline ของ task (attempt, `state_message`, error ของ task ที่ fail), timeline ของ update A ที่สั่งแยก และรายการ update ล่าสุดของ A (นับว่า task สร้าง update ซ้อนกี่ครั้ง, `cause`) |

verdict ของ Step 2:

| verdict | ความหมาย |
|---|---|
| `CONCURRENT` | ช่วง `RUNNING` ของ A และ B ซ้อนกัน > 0 วินาที (รันพร้อมกันได้) |
| `SERIAL` | ไม่ซ้อนกัน ตัวหลังเริ่ม `RUNNING` หลังตัวแรกจบ (ระบบ queue/รอเอง) ดู timeline ว่าตัวหลังอยู่ใน `QUEUED` หรือ `WAITING_FOR_RESOURCES` หรือไม่ |
| `A_REJECTED_AT_START` / `B_REJECTED_AT_START` / `BOTH_REJECTED_AT_START` | `start_update` ของตัวนั้น raise (ดูข้อความ error แบบคำต่อคำ) |
| `NEVER_RAN_<ตัวที่ไม่รัน>` | update จบ (เช่น FAILED/CANCELED) โดยไม่เคยเป็น `RUNNING` ดู error event |

ข้อจำกัดของการวัด: poll ทุก 5 วินาที จึงเห็นช่วงซ้อนที่สั้นกว่านี้ไม่ได้ (ถ้า A จบและ B เห็น `RUNNING` ในรอบ poll เดียวกันจะนับเป็น `SERIAL`)

### ผลที่คาดหวัง (สมมุติฐานก่อนรัน เพื่อเทียบกับผลจริง)

| step | สมมุติฐาน |
|---|---|
| 2 | Free Edition จำกัด 1 active pipeline ต่อประเภท จึงคาดว่าตัวที่สองถูก reject ตอน `start_update` (error ว่ามี active update/เกินโควตา) หรือถูก queue (`QUEUED`/`WAITING_FOR_RESOURCES`) แล้วรันหลังตัวแรกจบ ถ้าเห็น `CONCURRENT` แปลว่าข้อจำกัดนับต่อ update ที่ active ไม่ใช่ต่อ pipeline ที่ถูกสั่ง |
| 3 | `seq_ok=True` ทั้ง 2 task เพราะ `run_b` เริ่มหลัง `run_a` จบ ไม่มี pipeline อื่นรันซ้อน |
| 4 | task `run_a` ชนกับ update ที่ active อยู่ จึงอาจ fail (retry ครั้งที่ 2 หลัง 60 วินาทีอาจผ่านถ้า A ที่สั่งแยกจบแล้ว) หรืออาจรอจน A จบแล้วทำต่อ |
